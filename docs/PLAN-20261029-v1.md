# Nostalgex for Android TV — Foundation Plan

**Status:** draft for review · **Version:** v1 · **Date:** 29/10/2026
**Repo:** `Bolex80/Nostalgex` (public fork of `chadMueller/Nostalgex`)
**Upstream licence:** MIT. Name, icon and site are explicitly **not** covered by the grant, so this
project ships under its own name.

---

## 1. What we are building, precisely

Upstream Nostalgex turns a Plex / Jellyfin / Emby library into 139 scheduled "live" channels with an
EPG, a fixed daily schedule, and drop-in-mid-programme playback. It ships three surfaces:

- **tvOS app** — SwiftUI + AVPlayer, 29,977 lines of Swift (excluding 18,759 lines of tests).
- **Web tuner** — `plex-tuner.html` (9,933 lines) plus a shared engine in `scripts/*.js`
  (5,307 lines), driven by `channels.json` (125 KB) and `channels-memberships.json` (1.28 MB).
- **Docker container** — nginx serving a static build of that same tuner on :8080, plain HTTP.

There is no media of its own, no accounts, no server in the path. That is what makes an Android TV
client tractable: **we are not licensing or hosting content, only rendering a schedule over a library
the user already owns.**

**Goal:** the same schedule and the same feel, on Android TV — first on Alex's Xiaomi Google TV box
(HA model `MiTV-AFKR0`), then optionally across the household's Android TV fleet (six Philips
`TPM191E` sets, plus a bedroom Chromecast that has no app surface).

**Non-goal:** replacing upstream, forking the channel catalogue, or re-implementing the curation.

## 2. What already works, and what does not

Verified against the repo and the self-host documentation, not assumed:

- Upstream's own platform table records **"Google TV — TV Bro browser — Works"**, tested by the
  author on a real Google TV. So the tuner runs on our target OS *today*, with no code from us.
- `delegation` and model routing were verified live on the build host (`hermes -z -m <model>`
  returns a real completion for `glm-5.3:cloud`).
- Plex is reachable at `http://192.168.2.30:32400`, v1.43.5. No Docker on `ai-agents` (VM105);
  port 8080 is free there. Docker exists on the arr-suite LXC (`.85`).

What does **not** work, from upstream's own documentation:

- **Plex subtitles are unavailable in the web tuner** (Jellyfin/Emby have them). Real limitation for
  a household with children.
- **Surround audio on TV browsers is untested and frequently broken** — some TV browsers cannot decode
  AC3/DTS and play silently. This is the single most likely failure on our box.
- Browser UX: a mouse cursor, no launcher tile, no "what's on now" on the home screen.

**Conclusion: the gap is not the schedule or the guide. The gap is playback and 10-foot ergonomics.**

## 3. Architecture options

Four ways to get there. They are cumulative, not exclusive — each de-risks the next.

### Option A — Browser only (zero code)

Run the container, open the tuner in **TV Bro** on the Mi Box. Value: proves the API contract and the
audio reality in an afternoon. Cost: none. Ceiling: browser playback limits above.

### Option B — WebView kiosk shell (~1,500 lines Kotlin)

A real Android TV app: launcher banner, D-pad mapped to channel up/down, back handling, no browser
chrome, optional Leanback "now on channel 12". Reuses the tuner untouched. Still uses the WebView's
`<video>`, so **inherits every playback limit of A**.

### Option C — Hybrid player (recommended product target)

B, plus a native **Media3 / ExoPlayer** surface that takes over playback. The WebView keeps the guide,
the engine, the API clients and the schedule — so we never fork upstream logic. When a programme is
tuned, the tuner's resolved stream URL and headers are handed across a narrow JS↔Kotlin bridge to a
native player with a native OSD (channel up/down, mini guide, subtitle and audio-track selection,
sleep timer).

Why this is the right shape:

- It attacks **exactly** the two documented weaknesses: native audio/codec handling and subtitle tracks.
- It reuses 100% of upstream's logic, so `git merge upstream/main` stays clean indefinitely.
- It is bounded: roughly 4,000–6,000 Kotlin lines and a ~20-call bridge contract, not a rewrite.

### Option D — Full native port (rejected for v1)

Kotlin + Compose for TV re-implementing engine, API clients and UI. Reference point: the Roku port — a
faithful community port — is **27,018 lines** of BrightScript. Against an upstream pushing near-daily
(838 commits in 13 months), this is a months-long rewrite with permanent divergence. Revisit only if
this becomes a product we want to own outright.

**Recommendation: A this week → B in week 1–2 → C as the real deliverable. D never, unless the goal
changes.**

## 4. Phases and exit criteria

Each phase ends with a written artefact in the repo and a gate Alex signs off. No phase starts before
the previous gate passes.

### Phase 0 — Ground truth (3–5 days)

- Deploy the tuner container on `.85` (arr-suite LXC), pinned to a tag.
- Open it from the Mi Box over TV Bro; connect to Plex on `.30` over plain HTTP.
- Run an **audio/codec matrix** over real library items and record results per file.

**Exit criteria:** `docs/FIELD-REPORT-<date>.md` stating, per codec combination, what plays, what
downmixes, and what is silent — measured, not inferred. Plus `docs/ARCHITECTURE-<date>.md` describing
the schedule algorithm, the per-backend API contract, and the JS↔UI boundary.
**Gate:** Alex decides, on evidence, whether B and C are worth the spend.

### Phase 1 — WebView kiosk shell (4–6 days)

- New Android TV app module: launcher intent, TV banner, `LEANBACK_LAUNCHER`, min SDK for the Mi Box.
- Kiosk WebView pinned to the self-hosted tuner; injected D-pad mapping; back → guide, never exit.
- Session and credentials kept in app storage, never logged.
- Signed debug APK installable by `adb install`.

**Exit criteria:** installs and cold-starts to the guide on the Mi Box; channel up/down works from the
remote; 50 channel changes without a memory climb (`adb shell dumpsys meminfo`).

### Phase 2 — Native playback bridge (10–15 days)

- Media3/ExoPlayer surface composed above the WebView; seamless handover both ways.
- Bridge contract v1: tune, stop, seek-offset, subtitle track, audio track, playback state back to the
  tuner for reporting and OSD.
- Native OSD: channel number and name, what's on now/next, mini guide, sleep timer.
- Plex subtitle path: fetch subtitle as VTT via the server, render natively (closes the documented gap).

**Exit criteria:** the Phase 0 matrix re-run natively and **strictly better than the browser**: every
file that played in the browser still plays, and at least the AC3/EAC3 cases that failed now play or
downmix predictably. Subtitles render on a Plex title.

### Phase 3 — Parity and polish (8–12 days)

- Schedule parity: same programme at the same minute as upstream's manifest, spot-checked across
  midnight and a DST boundary.
- Stream quality mapping, playback reporting (Mark Watched), resume-after-starvation ladder.
- Leanback home-screen row ("now on"), settings screen, onboarding/connect flow with Plex PIN and
  Jellyfin QuickConnect.

### Phase 4 — Release (3–5 days)

- CI for Android only (`.github/workflows/android.yml`, separate from upstream's `ci.yml`): build,
  lint, unit tests, APK artefact on PR.
- Signing, versioning, `CHANGELOG.md`, README section, release APK.
- Upstream-sync job: weekly `git merge upstream/main` with a conflict report.
- Decision point: sideload-only, or a Play Store TV listing ($25 developer account, TV review).

**Honest estimate: 6–8 weeks of agent-assisted work.** The long pole is not coding — it is real-device
verification, which cannot be parallelised beyond one box without a second test device.

## 5. Agent roster

Eight specialist roles. **Never more than three live at once.** Roles are dispatched per task; they are
not permanent processes.

| # | Role | Model | Phase | Why this model |
|---|---|---|---|---|
| 1 | **Cartographer** | `kimi-k3:cloud` | 0 | Long-context code archaeology across 30k Swift lines, 9.9k of HTML and 1.4 MB of JSON; synthesis, not code. |
| 2 | **Field Tester** | `glm-5.3-flash:cloud` | 0 | Scripted, repetitive device probing: ADB, container deploy, codec matrix capture. Cheap and fast at volume. |
| 3 | **Android Platform Engineer** | `glm-5.3:cloud` (flagship) | 1–3 | The hardest code we will write: Media3 surfaces, JS↔Kotlin bridge, D-pad focus engine, lifecycle. Flagship capability earns its cost here only. |
| 4 | **Media Backend Engineer** | `deepseek-v4-pro:cloud` | 1–2 | Protocol semantics, not UI: Plex PIN, Jellyfin QuickConnect, Emby auth, pagination, stream-URL resolution. Correctness-critical reasoning. |
| 5 | **Compose UI Engineer** | `glm-5.3-flash:cloud` | 2–3 | High-volume, well-specified 10-foot UI: guide grid, OSD, settings, onboarding, banner assets. |
| 6 | **Verifier / Adversary** | `deepseek-v4-pro:cloud` | 2–4 | Independent acceptance harness, parity and DST tests, soak/leak runs. Must be a different model from the authors, and its job is to try to break the claim. |
| 7 | **Reviewer** | `kimi-k3:cloud` | all | Every PR, deliberately not the authoring model. Existing `reviewer` profile. |
| 8 | **Release Engineer** | `glm-5.3-flash:cloud` | 4 + ongoing | CI, signing, versioning, changelog, docs, upstream-sync. Mechanical plus writing. |

### Why this split

- **Flagship (`glm-5.3`) is used for exactly one role.** It is 9× the cost of flash and text-only; it
  is justified only where the code is genuinely hard (role 3). Everywhere else flash is sufficient.
- **`kimi-k3` owns reading and reviewing**, never authoring the code it reviews — review independence
  is the point.
- **`deepseek-v4-pro` owns correctness where a silent wrong answer is expensive** (auth flows, schedule
  parity, verification). It is not used for volume work.
- **`glm-5.3-flash` is the workhorse** for anything with a clear specification.

### Dispatch mechanics (verified, not assumed)

- `delegate_task` children all inherit one model — `delegation.model` (`kimi-k3:cloud` today). They are
  the runs that appear as **Subagent Session** rows in the Nesquena sidebar.
- To run a specific model instead, dispatch through the CLI:
  `hermes -z "<task>" -m glm-5.3:cloud --provider ollama-cloud --in <workdir>`. **Verified working**
  on the build host. These do **not** appear in the sidebar.
- Therefore: **phases are pinned model-homogeneous**, and `delegation.model` is changed at each phase
  gate (with the config guard's expectation table updated in the same pass, per standing procedure) so
  that the visible children in that phase run on the intended model. Isolated cross-model tasks use
  `hermes -z -m` and write their output into the repo.
- **Known pitfall to encode:** `glm-5.3` at `high`/`max` reasoning effort returns empty content on
  single-shot coding prompts (reasoning tokens exhaust the output budget). One-shot dispatches to it
  use `low` effort; agentic multi-turn work is unaffected.

## 6. Repository layout and git workflow

Keep the upstream tree **byte-identical** wherever possible, so upstream merges stay trivial.

```
androidtv/                  ← new: the Android TV app (Gradle project)
  app/                      ← module, Kotlin + Compose for TV
  bridge/                   ← JS↔Kotlin contract, versioned, with a contract test
  docs/                     ← per-module notes
docs/
  PLAN-20261029-v1.md       ← this file
  ARCHITECTURE-*.md         ← Phase 0
  FIELD-REPORT-*.md         ← Phase 0
  ADR-*.md                  ← decisions with the reasoning that produced them
.github/workflows/
  android.yml               ← new; upstream ci.yml untouched
CHANGELOG.md                ← new
```

Rules:

- `main` tracks upstream. Weekly `git merge upstream/main`; conflicts confined to `androidtv/` and
  `docs/`, which upstream never touches.
- Work on `plan/…`, `feat/…`, `fix/…` branches; every change lands as a PR reviewed by role 7.
- Household file convention: `-YYYYMMDD-vN` before the extension, and a `CHANGELOG.md` entry per
  version.
- **Never modify upstream-owned files** unless a hook is unavoidable; when it is, the change goes
  behind a documented adapter and is listed in `docs/ADR-*.md` so an upstream merge can be judged
  quickly.

## 7. Definition of done (Phase 2 target)

Each item is measured on the Mi Box and written into the field report:

1. Cold start to guide under 5 s with a 1,000+ item library.
2. Tune → picture in under 3 s; join offset matches the schedule.
3. Audio matrix: H.264+AAC, H.264+AC3 5.1, HEVC+EAC3, HEVC+DTS — each plays or downmixes predictably.
4. Subtitles: external SRT renders; PGS documented as unsupported or server burn-in.
5. 50 channel changes with no memory climb.
6. Sleep timer fires; playback stop is reported to the server (confirmed in Tautulli).
7. Two-hour soak: no OOM, no A/V desync.
8. Network cut mid-play recovers per upstream's starvation ladder.

## 8. Risks

- **Audio decode on the Mi Box** — highest likelihood, highest impact. Mitigated by Phase 0 being a
  measurement phase, not an assumption.
- **Bridge drift against upstream** — mitigated by a narrow, versioned contract and a contract test
  that runs in CI on every merge.
- **Play Store review for WebView-heavy apps** — mitigated by shipping sideload first and treating a
  store listing as a separate decision.
- **One test device** — verification is the bottleneck. A second Android TV test target would roughly
  halve Phase 2–3 calendar time.
- **Fork rot** — mitigated by the weekly upstream merge being a scheduled job, not a good intention.

6. **Where the container lives** — arr-suite LXC (`.85`, Docker present) or bolex-cloud; or install
   Docker on `ai-agents`.
